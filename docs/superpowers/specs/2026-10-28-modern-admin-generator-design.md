# 现代后台项目生成器改造设计

状态：用户已于本会话确认整体方案并要求开始改造；组件库明确为 Ant Design Vue。正在编写实施计划，尚未开始产品代码实施。

## 1. 目标与依据

用户确认以 `prototypes/inventory-admin.html` 的后台列表方向改造生成器，要求现代、美观、便捷，类似轻量 Vue Admin / 若依后台，而非营销网站。插画和图标应贴合需求风格，生成工程应便于扩展。

原型是视觉与操作方向参考，不是直接复制进生产的底座，也不证明生成链路已经实现这些能力。原型的青绿色、库存业务与品牌名不是固定输出。

本次生成单位从散列展示区块提升为具有业务结构的后台页面，继续沿用受校验的结构化 draft/spec → 确定性代码生成 → 图片 → 构建流程。

## 2. 范围

本轮包含：后台布局、导航、页面结构、核心前端交互、主题与图像槽位、生成工程组织、生成约束和验收。

不包含：真实 API 层、数据库、登录认证、RBAC、后台服务、生产部署；不实现若依全部功能，不预置无关的用户/角色模块，不做拖拽编辑器。

现有官网生成能力保留，但后台页面不得继续复用官网区块间距和容器宽度。现有任务、预览、源码与 dist 导出流程保留。

## 3. 当前限制的代码依据

- `packages/templates/vue3-base/src/layouts/SidebarShell.vue`：目前只是纵向 NavBarSimple 与 slot。
- `packages/templates/vue3-base/src/styles/base.css`：通用 container 最大 1120px，section 使用大间距；DataTable 复用这些类。
- `packages/codegen/src/page.ts`：页面主要串联区块；表格 edit 直接发送原行并 update，缺少编辑界面流程。
- `packages/providers/src/openai-spec-drafter.ts`：已有后台提示词，但视觉限制过于单一，且关于 landing 切壳的描述与实际 pickShell 不符。
- 模板当前只依赖 Vue 和 Vue Router，没有成熟后台控件库。

## 4. 技术方向与边界决定

以下为设计方建议，随本设计整体审批，不视为用户已经逐条选择：

1. 新增独立的 Vue 3 后台底座，复用现有构建技术链；官网底座保持隔离，不把后台组件库强塞进官网产物。
2. 用户明确指定后台使用 Ant Design Vue，作为表格、表单、抽屉、分页、反馈等基础控件，避免继续手写不完整的基础交互。实施计划优先核对仓库 web 控制台已使用的版本，并锁定与生成底座 Vue/Vite 兼容的稳定版本，资产随工程打包，不依赖运行时 CDN。
3. 自有组件负责后台布局、页面组织和主题适配；基础库不直接规定所有视觉。限制全局覆盖，利用 CSS 变量与命名空间实现换肤。
4. 功能图标使用打包的 SVG 图标库与受控名称映射，禁止模型输出任意可执行 SVG/HTML。插画与业务装饰图标可由图片模型生成，功能图标不等待生成图片才能使用。
5. 本轮前端数据仍为 mock，但通过独立的数据模块与 composable 供页面访问；不新增 HTTP 客户端。演示的刷新重置特性明确记录。

## 5. 项目类型与兼容

新增可选项目级体验声明 `experience.kind = admin | marketing`。后台声明中承载导航与页面模式配置；旧 spec 缺省保持现有类型推导规则。

新生成后台任务必须显式声明 admin，使用后台底座和后台组件允许列表。校验器拒绝 admin 中的 Hero、Pricing、营销 CTA 等区块，提供可修复错误，走现有起草重试而非静默降级。

不要仅以关键词硬判断；模型结合完整需求选择类型，再由 schema 和组件兼容校验保证一致性。混合站点本轮不新增复杂多壳能力：按项目声明使用主壳，auth 页面采用无导航独立布局。营销与旧 spec 的兼容行为应有回归测试。

布局和导航由同一份结构化声明派生。导航支持一级分组与子菜单、图标键、顺序和隐藏详情页；所有导航叶子必须指向已声明路由，禁止悬空链接和仅装饰的功能入口。详情页不必出现在菜单中，通过列表操作进入。

## 6. 后台底座

布局包含：可折叠侧栏、顶部栏、由路由派生的面包屑、页面标题与辅助说明、统一内容区。登录/认证样式页独立显示，不伪装成真正认证。

原型的页面标签外观可保留为当前页面标识；本轮不实现浏览历史多标签、标签缓存与跨页表单保活。不要显示无法使用的关闭标签按钮。

桌面内容利用可用宽度，页面间距约 16–24px，控件默认舒适紧凑。平板折叠菜单，手机改为可打开的导航抽屉；表格仅在自身容器横向滚动，不能把整页撑宽。

不固定库存模块、品牌、菜单数量或管理员身份。仅生成需求相关的业务模块。没有行为的通知、设置、头像下拉按钮不应出现。

## 7. 业务页面模式

在现有 pageType 上增加后台专用的可选类型化页面配置，至少支持 list、detail、form、workbench、settings。配置字段、允许组合、绑定关系由 schema 约束，具体命名留给实施计划。

### 列表页：第一验收重点

固定职责区：页面标题 → 筛选表单 → 列表操作栏 → 表格 → 分页；弹窗/抽屉位于页面之外，不作为连续展示区块。

- 支持关键词、枚举等与数据模型一致的筛选；查询和重置可用。
- 支持分页、行选择、清晰的状态标签、格式化金额/日期、空状态。
- 需求声明新增/编辑时生成表单与打开/保存/取消流程。编辑回填当前行，取消不污染原数据，保存后更新列表。
- 支持详情查看；支持单条删除与显式批量删除时的确认。上下架等状态动作只在模型定义相应枚举/布尔字段及动作时出现。
- 搜索结果变少、删除最后一行、换页之后，页码和选择状态必须合法。
- 表单依据字段类型与校验定义生成，不猜测未声明的业务校验。
- 按钮必须具有真实的本地演示行为；不能以空 handler 或成功 toast 冒充操作完成。

新增动作声明必须有类型化语义、目标与字段约束，禁止自由代码。保留旧 operations 兼容路径，新后台模式不使用无操作兜底掩盖不支持的行为。

### 其他页面

- detail：信息分组、状态、相关记录（存在模型关系时）和返回列表。
- form：分组字段、校验、提交/取消与明确反馈。
- settings：分组设置与保存反馈，不假装配置了真实服务。
- workbench：只使用与业务数据相关的摘要、待办和快捷入口；不默认堆满指标卡，不增加营销横幅。统计从 mock 集合派生，避免与列表矛盾。复杂图表和关系查询不是本轮必需能力。

## 8. 视觉定制与图片

将布局密度与品牌风格分离。后台始终保持清晰的信息层级，但可以根据需求变化主辅色、浅/深侧栏、圆角、字体层级和插画艺术风格。不再在 prompt 中强制所有后台都是浅灰低饱和蓝、小圆角。

定义语义化 token：背景/面板/边界、正文/次要文字、主色及悬停/选中态、成功/警告/危险，以及控件高度、页面间距、行高。主题主色不能覆盖语义状态色；提供可见键盘焦点与足够文字对比度。

插画只用于登录、空状态、引导和小型欢迎区域；正常列表不能被大图占据。沿用 styleBible、图片缓存和后处理。图片几何仍只来自组件侧车，模型只填主题 prompt/alt，不放宽既有插槽不变量。

新增图像槽位时同步注册表、派生逻辑与组件实现。插画失败沿用现有生成失败/重试机制，不新增未经设计的占位成功策略。

功能图标以语义键映射到同一图标系统，保持描边和尺寸统一；品牌/业务装饰图标可走受控图片插槽。需要纯线性/圆润等风格时在有限可用图标集内选择，不承诺任意图片风格的功能图标都能自动生成。

## 9. 生成工程扩展性

产物建议职责划分：

- layouts：后台壳与导航。
- components/admin：页面容器、筛选/操作栏等公共业务组件。
- modules/<module>：该模块页面、表单、类型与本地状态封装。
- router 与 navigation：路由及菜单配置，由统一声明生成。
- theme：token 和主题入口。
- data/mock：独立示例数据及访问适配。
- assets：已生成插画和装饰资产。

模块与文件名由校验后的安全标识生成，沿用路径/字符串安全约束。公共组件不包含具体库存或客户业务名；新增模块不需要修改布局。源码包含简短说明：启动方式、菜单入口、主题入口、模块组织、mock 边界和后续对接位置。

## 10. 验收

1. “库存管理后台”生成有业务菜单、筛选表格、分页、新增/编辑抽屉的完整 Vue 工程，视觉达到已确认原型方向，而不是官网段落。
2. 再用不同业务和风格需求生成一例，验证不是硬编码库存数据和绿色主题；路由、字段、菜单及资产符合该需求。
3. 新增、编辑、取消、筛选/重置、分页及声明的状态/删除操作，在浏览器中真正可用；无空操作和虚假保存。
4. 新后台产物必须通过 vue-tsc 与 vite build；不能以现有默认跳过 typecheck 作为验收依据。
5. 检查桌面和手机宽度：无整页横向溢出，导航可用，表格局部滚动，抽屉可键盘关闭并正确管理焦点。
6. 主题切换与业务语义分离；图片/图标位置合理，没有大幅营销装饰占据业务区域。
7. 旧官网与旧 spec 回归通过；任务进度、预览、源码和 dist 导出保持可用。
8. 真实模型端到端运行依赖有效凭证与外部服务；如不可用，明确区分固定 draft 验证与真实生成验证，不能声称后者已通过。

## 11. 实施裁定与后续流程

以下是可实施性检查后由设计方明确的技术默认，不是额外扩展需求：

- 整体计划覆盖 list、detail、form、workbench、settings 与视觉策略；先完成底座与列表是执行顺序，不是缩减最终范围。
- 缺省 experience.kind 的旧 spec 保持旧底座和旧区块路径；只有显式 admin 使用新底座。新 admin 使用类型化页面模式，不再任意拼接旧 DataTable/FormPanel 等业务区块。插画类区块仅在声明的兼容插槽中使用。
- collections 与 forms 是唯一模型源。新页面配置引用它们；后台专用动作放在新配置的 actions 中，旧 operations 不改变语义。admin 中不支持的旧 operations 必须报错而非静默忽略。
- 新后台的真实构建链必须执行 vue-tsc，失败按现有 building → failed 机制报告；旧类型检查开关行为保留，不新增自动构建重试策略。
- “主题切换”验收指不同需求生成不同主题并保持语义色正确，本轮不要求运行时换肤开关。
